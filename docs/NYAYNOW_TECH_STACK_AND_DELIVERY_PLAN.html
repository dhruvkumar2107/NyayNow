01Executive summary

NyayNow is an India-first legal technology platform that combines AI-assisted legal information, document workflows, advocate discovery and practice tools in one product. It is currently positioned as v2.0 Beta at www.nyaynow.in.

The product deliberately separates three things that are often blurred in legal tech: (1) general legal information, (2) workflow tools such as drafting and case tracking, and (3) access to a human advocate through a marketplace. The public site repeats a clear caution: AI output is not citation-verified today, Legal SOS is not an emergency dispatch service, and lawyer credentials must be independently confirmed.

Technically, the repository is a working monorepo: a Next.js 15 / React 19 frontend, an Express 4 API with Socket.io, a small FastAPI AI service, and MongoDB Atlas with 25 collections. Production runs on Vercel and Render, with Cloudinary for media, Google Gemini for generation, Razorpay for payments, and a long list of optional integrations (Algolia, Brevo, Twilio/MTalkz, Bhashini, Setu/DigiLocker, Indian Kanoon, DocuSign, Sentry, PostHog).

This document converts that working system into a delivery plan. It assigns three workstreams with explicit boundaries, sequencing and acceptance criteria. The sequencing principle is simple: keys and database first, environments second, feature work in parallel, launch last. Dhruv’s key and database work unblocks Rudraksh’s deployment and Tejas’s HR data model; Rudraksh’s staging environment unblocks end-to-end testing; Tejas consumes both to ship the careers portal and frontend hardening.

5.2 Frontend implementation notes

  • App Router with route groups for public marketing, product tools, dashboards and admin. Client components are used where interaction demands it; SEO pages remain server-rendered.
  • Standalone output enabled for container builds. Docker image runs `node server.js` on port 3000.
  • CSP middleware generates a per-request nonce; inline scripts must carry the nonce. Third-party origins (Sentry, PostHog, Google, Razorpay, Cloudinary) are explicitly allowlisted.
  • API proxying: the browser calls same-origin `/api/*`; Next rewrites to the Express service using `NEXT_PUBLIC_API_URL`. This keeps cookies first-party and avoids broad CORS in the browser.
  • Design system: Tailwind tokens plus shared components; navy/gold brand palette; avoid one-off hex values in feature code.
  • i18n: 14 locales, including RTL Urdu. Layout must be tested with `dir="rtl"`, not only translated strings.
  • Performance: route-level code splitting, image optimisation, font discipline, and a budget for the assistant screen on mid-range Android.

06Architecture & data flow

The system is a three-tier web application with an AI sidecar. The browser talks to Next.js; Next.js proxies API calls to Express; Express owns authentication, business rules and persistence; FastAPI handles heavier AI orchestration; MongoDB and Cloudinary hold state.

7.1 Data rules that must hold

  • Payment idempotency: a unique index on the provider event ID is mandatory; processing must be safe under retries and out-of-order delivery.
  • Plan consistency: reconcile the legacy enum (silver, gold, diamond) with the public plan names (pro, gold, firm) before billing changes. One source of truth, migrated deliberately.
  • PII minimisation: do not persist full legal queries, documents or chat content longer than needed. Define retention per collection and support erasure requests.
  • Verification truth: advocate verification is a state machine (pending → verified / rejected) with an audit record; the UI must never infer verification from profile completeness.
  • Soft delete: use deletedAt for user-facing records where recovery or legal hold is needed; hard-delete media from Cloudinary on erasure.
  • Time zones: store UTC; render in Asia/Kolkata. Court dates are date-only and must not shift across time zones.

Migration discipline

MongoDB is schemaless at the database level but not at the application level. Every schema change needs a forward migration script, a rollback note, and a staging run against a production-like snapshot. Never run ad-hoc updates directly on production.

8.1 Contract rules

  • Validate at the edge: every body, query and param is validated before hitting the database or an AI provider.
  • Consistent errors: { error: { code, message, requestId } }; never leak stack traces or provider messages in production.
  • Pagination: cursor-based for high-volume lists; hard maximum page size; no unbounded queries.
  • Idempotency: mutation endpoints that can be retried accept an idempotency key; payment webhooks are idempotent by provider event ID.
  • Versioning: prefix breaking changes (/api/v2) rather than silently changing response shapes.
  • Timeouts: provider calls have explicit deadlines; AI requests fail closed with a clear retry path.
  • Documentation: maintain an OpenAPI file for the Express API; generate examples from tests, not memory.

10Delivery plan by workstream

Three owners, deliberately separated by system boundary. Dhruv owns the inputs (keys, database, provider accounts). Rudraksh owns the runtime (environments, deployment, reliability, backend). Tejas owns the human interface (HR/careers frontend, design system, accessibility, conversion). The plan assumes part-time founders, not a full-time engineering org, so sequencing matters more than parallelism.

Sequencing principle

Unblock, then build. Dhruv’s key/database work and Rudraksh’s staging environment are prerequisites for reliable feature work. Tejas can start design and static UI immediately, but must not wire production data until staging and schemas are agreed.
